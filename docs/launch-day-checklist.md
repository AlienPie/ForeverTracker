# Launch-day checklist

One ordered list. Do it top to bottom on launch day. For each item: what to check, how, and what a failure means. Nothing here needs a code change to attempt; failures are collected and taken back to a developer session (see the last section).

Sources: spec section 12 item 4, the addon API assumptions recorded while building the collectors, and the unverified ForeverDB response shapes.

## A. Prepare (before logging in)

1. **Run the server.** Build and run the image per `README.md`, then `curl -s localhost:3000/api/health` returns `{"ok":true}`. Failure: the container is not running (`podman logs`), or the port or `DATA_DIR` volume is wrong.
2. **Create a device token.** `podman exec forevertracker node /app/create-token.mjs launch`. Keep it somewhere private. Failure: the data volume is not writable by the container user.
3. **Check the ForeverDB API shapes.** Put your key in the environment without leaving it in shell history or any committed file: `read -rs FOREVERDB_API_KEY && export FOREVERDB_API_KEY`, then `pnpm tsx tools/live-check.ts`. Expect the build string, level cap and remaining daily quota. Failure: the key is wrong, the API changed, or the `/meta` shape differs. Then run a first `pnpm content:sync`. Only `/meta`, `/quests` list rows and `/classes/mage` have real captured samples. Everything else (zones, vendors, dungeons, other class details, professions, gathering, and the pagination of detail endpoints) is an unverified guess: check that the sync finishes without a shape error and that each resource stored records. Failure: note the resource and the error; the mirror code for that resource needs adjusting to the real shape.
   - Where it writes: `DATA_DIR` is optional for `content:sync`. Unset (or relative), it resolves like the server and token CLI: `./data-local` under the workspace root, giving `data-local/forevertracker.sqlite` on the host. It does NOT write into the container's `ft-data` volume. The sync tooling needs `tsx` and is not in the image, so it cannot run inside the container. In M0 the host mirror and the container's volume are therefore separate databases. The key is read only from the exported `FOREVERDB_API_KEY`; `.env` is not loaded by the CLI.
   - Check the mirror from the host (no sqlite3 CLI needed; the command was verified against a freshly created database): `cd packages/db && node -e 'const D=require("better-sqlite3"); const db=new D("../../data-local/forevertracker.sqlite",{readonly:true}); console.log(db.prepare("SELECT resource, count(*) AS n FROM content_record GROUP BY resource").all())'`. Each synced resource should show a non-zero count.
   - Alternative, UNTESTED: have the container use the host file by bind-mounting the directory instead of the volume: `-v "$PWD/data-local:/data:Z"` with `-e DATA_DIR=/data`. Pitfall under rootless Podman: your host user is not mapped to the container user `node`, so `/data` is not writable and the server fails to open the database. Remedies: add `--userns=keep-id` (and run as your uid, e.g. `--user "$(id -u):$(id -g)"`), or run `podman unshare chown -R <node uid>:<node gid> data-local` first. Check `podman logs` if the server will not start.

## B. In game: install and first run

4. **Install the addon** as described in `README.md`. Check: it appears in the AddOns list and loads with no Lua error popup. Failure: the `.toc` Interface number (16001) may not match the Forever client, or the `\` path separators in the `.toc` are not accepted. Look for "out of date" or "failed to load" in the list.
5. **Log in and play a minute**, walk into a new subzone, then `/ft sync`. Check: chat prints `ForeverTracker: snapshot saved. Type /reload to write the data file to disk.` and no error appears; then type `/reload` yourself. (`ReloadUI()` from the addon was observed to be BLOCKED on this client, so the addon no longer calls it.) Failure modes: the line `could not save a snapshot` or a Lua error means a WoW API differs. Note the error text exactly. Also check that `C_Timer.After` exists: if it is absent, `/ft sync` finishes immediately and may save a stale played time (see item 16).
6. **Locate SavedVariables.** Find `WTF/Account/<ACCOUNT>/SavedVariables/ForeverTracker.lua` (Wine/Proton and macOS paths are in `README.md`). WoW names this file after the addon folder / `.toc` name, not after the `ForeverTrackerDB` variable; if the file on disk is named differently, use the actual name everywhere below and record it. Check: the file exists and its modification time is just after the `/ft sync`. Failure: a different path (record the real one and update the README), or the file is only written at logout or `/reload` (type `/reload` after `/ft sync`).

## C. Upload and inspect

7. **Upload the file** with the curl command from `README.md`. Expect 200 with `stored: 1` per character, `failed: 0`. Failure: 401 means a bad token; 413 means over 8 MB (the quest probing or event log may be too large; note the file size); 422 means the parser rejected the file (note the line and column in the reply). If `time()` is missing in the client, the addon writes `takenAt = 0` for every snapshot. Ingest then stores the first upload for a character (`stored: 1`) and SKIPS every later upload for it (`stored: 0`, `skipped` rising), because `(guid, takenAt = 0)` already exists. So if the first upload works but later uploads of changed data always report `stored: 0`, check that `takenAt` in the SavedVariables file is a real unix time and not 0.
8. **Inspect what was degraded and what was stored.** Two procedures, in this order.
   - (A) Primary, no database needed: on the host, open the original SavedVariables file (path from item 6) and run `grep -n "unavailable" <path>/ForeverTracker.lua`, then read the surrounding lines inside the `ForeverTrackerDB` table. This is the source of truth: each `unavailable = true` section carries a `reason` saying which API is missing or behaves differently.
   - (B) What the server stored: the image has no `sqlite3` CLI, and the database is in WAL mode, so do not copy the `.sqlite` file out alone (recent rows may still sit in the `-wal` file). Instead read it read-only with the container's own better-sqlite3 (replace `forevertracker` with your container name):
     ```sh
     podman exec forevertracker node -e '
     const D = require("/app/node_modules/better-sqlite3");
     const db = new D("/data/forevertracker.sqlite", { readonly: true });
     const q = "SELECT guid, taken_at, build, schema, unsupported, raw FROM snapshot s WHERE taken_at = (SELECT max(taken_at) FROM snapshot WHERE guid = s.guid)";
     for (const { raw, ...meta } of db.prepare(q).all()) { console.log(JSON.stringify(meta)); console.log(raw); }
     '
     ```
     It prints, per character, `guid`, `taken_at`, `build`, `schema` and `unsupported` and then the raw JSON of the newest snapshot (table `snapshot`, primary key `(guid, taken_at)`). The addon's event log is stored separately in table `character_event` (`guid, t, kind, data`) and `visited`/`taxi`/`played` in `character.extras` (JSON). `unsupported: 1` means the file's schema version was not understood. Search the raw JSON for `unavailable` to cross-check (A).
   Failure: record each section and reason (items 9 to 17 say what each means).

## D. API assumptions to confirm from the stored snapshot

For each item, look at the named section of the stored JSON. A missing or `unavailable` section is the failure signal unless noted.

9. **Build string.** `snapshot.build` looks like `1.60.1.70707` (version, then build number) and matches the `build` from `live-check`. Failure: `GetBuildInfo` returns a different layout, so ForeverDB content cannot be matched to the client build.
10. **Identity.** In `identity`, `class` and `race` are upper-case tokens (for example `MAGE`), `faction` is English, `name` has no `-Realm` suffix, `level` and `xp` are numbers. Failure: a token or English assumption is false, or `UnitXP`/`UnitXPMax` are missing.
11. **Position and zone.** In `state`, the zone name, subzone, map id and position are present (position can be nil inside instances). Failure: `C_Map.GetBestMapForUnit` or `GetPlayerMapPosition` is missing. `GetMoney` is also read here: check that the money value is a number (copper); failure means `GetMoney` is missing.
12. **Equipped items.** `state.equipped` is keyed by slot name (for example `"HeadSlot"`) with item ids taken from `item:ID` links. Failure: empty or wrong ids mean `GetInventoryItemLink` slot numbering (0 to 19, 0 = ammo) differs on this client.
13. **Talents (trait nodes).** In `progress`, the talent capture reads `C_ClassTalents.GetActiveConfigID`, `C_Traits.GetConfigInfo`, `GetTreeNodes` and `GetNodeInfo().currentRank`, plus unspent points from `C_Traits.GetTreeCurrencyInfo`. Check that the ranks and unspent points match what the talent window shows. Failure: the section is `unavailable` or wrong; the legacy fallback uses `GetTalentInfo` (5th return = rank) and `UnitCharacterPoints`. Also check these APIs work out of combat and are not protected.
14. **Professions.** The `progress.professions` list is `{ skillLine, name, rank, max }` and matches your skills window. Failure: `GetProfessions`/`GetProfessionInfo` may be absent or have different return positions (name 1st, rank 3rd, max 4th, skillLine 7th; `GetProfessions` returns up to 5 indices: two professions, archaeology, fishing, cooking). If the English-only fallback was used, `skillLine` is 0 and a non-English client may give an `unavailable` marker. Check the skill line ids too (171, 164, 333, 202, 165, 197, 182, 186, 393, 185, 129, 356). The English-only fallback also relies on the 13-return layout of `GetSkillLineInfo` (rank is the 4th return, max rank the 7th); a wrong layout shows up as wrong or missing ranks when `GetProfessions` is absent.
15. **Quests.** `progress.questLog` lists current quests (`C_QuestLog.GetNumQuestLogEntries` first return, `GetInfo(i)` giving `questID` and `isHeader`). Per-ID completed-quest probing is only as good as the ID list the addon has, so `progress.questsCompleted` is likely empty at first. Also time the logout or `/ft sync`: probing thousands of IDs must not hitch. Failure: a slow logout means the probe must be cut down or made incremental.
16. **Played time.** After a `/ft sync` (or after any login: the addon requests `/played` once on initial login, which prints one "Total time played" line to chat) the top-level `time` section has `played`, `playedLevel` seconds and `at` (unix time measured). The value is persisted per character, so after a `/reload` it is still present with its older `at`. `TIME_PLAYED_MSG` args are (total, level) and `RequestTimePlayed` also prints `/played` to chat (expected). Failure: `time` stays `unavailable` or stale; the 2-second timeout may be too short or the event never arrives.
17. **Visited places and flight paths.** `exploration.visited` grows as you cross zones and subzones (events `ZONE_CHANGED`, `ZONE_CHANGED_INDOORS`, `ZONE_CHANGED_NEW_AREA` should fire and `GetRealZoneText`/`GetSubZoneText` return names). Open a flight master map: `exploration.taxi` should list node ids. Failure for taxi: the taxi API may not exist or reports a zone map instead of the continent, so nodes may be missing or partial (the addon prefers `GetTaxiMapID`, then `GetBestMapForUnit`). Failure for visited: the events or text APIs differ.
18. **Events fire as expected.** After levelling up or turning in a quest, the `events` array has `level_up` (arg 1 = new level) or `quest_turned_in` (arg 1 = quest id) entries. After learning a profession or raising a skill rank, one `profession_changed` entry (with `data.count`) appears; repeated skill events with no change log nothing. Failure: an event name is not valid on this client (each registration is guarded, so an invalid name is silently skipped; a missing entry is the only symptom).
19. **Timing and flush.** Confirm SavedVariables are written on `/reload` and on logout, and that the last good snapshot survives (no snapshot is taken at logout; the 2-minute autosave, login and event saves keep it fresh). Failure: a degraded or stale snapshot after logout.

## E. Product questions to settle on the day

20. **Forever loadout strings.** Check whether Forever loadouts can be imported and exported as strings; the talent playground depends on this. Failure: plan the playground around manual entry.
21. **Tooltip provider.** Test Wowhead `/forever/` links and ForeverDB's embed and pick the default.
22. **Content freshness.** If ForeverDB has not agreed to a local copy, keep `CONTENT_MODE=mirror` and watch the daily quota; switch to `on-demand` if refused.

## What to bring back to the developer session

- The raw `ForeverTracker.lua` file with the `<ACCOUNT>` folder name redacted (and character names if you prefer; they are data, not secrets). Do not include tokens or your API key.
- The exact text of any Lua error, the output of `live-check` and the first `content:sync` (without the key).
- The real SavedVariables path on your system, and your notes for items 4 to 22: pass or fail, with the `reason` strings from any `unavailable` section.
