R13 (Task 6) `ContentSource.list` takes `opts?: { limit?: number; offset?: number }` ONLY (not an arbitrary query record). Reason: the mirror cannot honour API-side filters, so a free-form query would behave differently per mode. Filtering is done in memory by the advice engine over the returned rows. `mirror` mode serves `listRecords(db, resource, opts)` and makes no API calls; `on-demand` mode calls `client.get('/<resource>', { limit, offset })` (defaults limit 25 per the API) and `client.get('/<resource>/<id>')` for `get`, caching each distinct request for 60,000 ms in memory. A `get` miss (record absent / API 404) returns `null` in both modes; other errors propagate. Resource names map 1:1 to API paths (`quests` -> `/quests`).

R14 (Task 7) Ingest edge cases the plan leaves open: (a) if the parsed file has no top-level `ForeverTrackerDB` table (missing or not an object) `ingestSavedVariables` throws a typed `IngestError` with a clear fixed message (Task 8 maps it to HTTP 422); a `LuaParseError` from the parser propagates unchanged. (b) `characters` absent or empty -> returns all-zero summary, no error. (c) A character entry whose `snapshot` is missing or lacks a numeric `takenAt` is counted in `skipped` (not stored, no character row) and never aborts the other characters (each character is processed in its own transaction and its own try/catch; only IngestError for (a) and unexpected DB failure abort). (d) `schema` missing or non-numeric on the file is treated as unsupported (stored raw, `unsupported = true`, no extraction). (e) `snapshot.schema` column stores the file's `ForeverTrackerDB.schema` value (integer; use 0 if non-numeric); `snapshot.build` stores `snapshot.build` or "" if absent. (f) `Snapshot` types follow the plan exactly, with `equipped` keyed by slot NAME strings (R4). (g) Summary semantics: `stored` = newly inserted snapshot rows; `skipped` = already present (same guid+takenAt) or malformed; `unsupported` = stored rows that were marked unsupported (counted in `stored` too); `characters` = number of distinct characters seen with a valid snapshot.

R14-clarification (Task 7 fix round 1; supersedes the last clause of R14c and the counters in R14g): R14c was self-contradictory. Corrected rule: each character is processed inside its own try/catch; ANY error thrown while processing one character (including a DB error) is caught, that character is counted in a new summary field `failed`, and the remaining characters are still processed. Only the file-level conditions in R14(a) (IngestError) and a `LuaParseError` abort the whole call. The summary type becomes `{ characters: number; stored: number; skipped: number; unsupported: number; failed: number }` (`failed` is 0 normally; a failed character is NOT counted in `skipped` or `characters`). The error is not rethrown and nothing sensitive is logged. Task 8 returns the summary as-is with HTTP 200 (the client can see `failed`).
